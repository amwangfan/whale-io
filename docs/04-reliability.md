# 04 · 可靠性设计：重传纪律、大分片、断路器

## 先校准预期

BLE 链路层本来就可靠（CRC + 链路层重传），所以**应用层逐包回执大多是冗余的**——但「明显提速 10 倍」也是乐观话：一帧 64KB 里往返开销约 4s、纯数据传输约 3s（原始吞吐 ~190kbps），消掉往返也只能到 **2-4 倍**（7s → 2-3s）。规划时按这个量级来。

## 有界重试 + 失败隔离（帧级）

手机侧实现（纯策略类，可单测）：

- 每帧最多重试 3 次；丢帧记录但**不阻塞后续帧**（失败隔离）；
- 连续丢 3 帧触发**断路器**：冷却 60s 或重连后恢复，不硬怼一条烂链路；
- 整帧重试 = 用新 tx 重发 BEGIN（依赖固件「新事务重置卡帧」语义——新事务到来意味着上一帧已被放弃）；
- 重试经调度器 tick 暂存，**不在回执回调里内联重发**（会卡死队列）；
- NO_SESSION / STALE / 协议拒绝类 = 致命，不重试，走恢复握手（见 03）。

## 大分片：性价比最高的提速

- 默认 512B/包是双端保守值；协议和固件处理器本就支持到 16384B（MAX_RECT）；
- 厂商分包器会按 MTU 自动分段，所以**手机侧只调两个常量**（分片像素数/包长），固件侧把包长上限做成编译期档位（512/2048/4096/8192/16384，非法值编译期 `#error`）；
- 效果：139 包 → 33 包（2K 档）乃至 ~5 包（16K 档），少掉一百多次往返；
- **唯一离线定不了的**：对端文件接收缓冲吃不吃得下大包——真机梯度验证（2K→4K→8K→16K），从保守档开始爬；
- 净荷 = 包长 − 40（信封开销），用编译期表达式 + `_Static_assert` 钉死，别让两个常量漂。

## 千万别动的

**全局单闸门**（传输门）：它被 OTA/相机/卡片/读书/音乐/显示/问候等七八个功能共用。滑动窗口/NAK 这类重构要动它——一处崩全盘。我们的结论：先做大分片（不碰闸门），窗口化等数据证明有必要再说。

## 验收纪律

- 档位默认 512 档的产物必须与已验证版本**逐字节一致**（防止改档逻辑误伤现行行为）；
- 高档位离线全验（编译零未定义符号、主机测试整帧上屏、仿真五档全过）后才上真机；
- 真机梯度：2K→4K→8K→16K 逐档验证，不过就停在该档。
